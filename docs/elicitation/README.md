# Elicitation record

The student survey covers how people search for rooms. The library and OIT questions cover the two services the project depends on.

| Source | Question to put to the source | Current evidence |
| --- | --- | --- |
| Enrolled UTD students | How often do room seekers have to check again? Which delay, watch cap and channel fit their workflow (Q5)? | [Pilot-ready survey](survey-draft.md). Pilot target: ten enrolled students. |
| McDermott Library reservations/systems staff | Is there a supported credential-free read? How many rooms/dates does a response cover? What cache rules, allowed rate and backoff apply? May an unofficial service alert students (Q1/Q2)? | [Public inventory observation and controlled experiment](../spikes/availability/README.md). Lee will confirm the permitted source and rate with library staff. |
| McDermott Library reservations staff | Which restrictions depend on the individual student, and which availability fields reliably describe capacity and bookable times (Q4)? | P1's interim definition uses the library's free flag. Actual eligibility is decided on the library booking page. |
| UTD OIT and campus accessibility staff | Can this project register for NetID SSO? Which claims establish enrollment and supply email? Which accessibility standard applies? Can a watch retain a push subscription (Q3/Q6)? | The [constraints](../constraints.md) depend on which identity claims and accessibility guidance OIT provides. |

After each conversation, record the date, the stakeholder role, the question, a de-identified summary and its effect on the requirement IDs. The member who conducts the elicitation should commit the summary and link its review. Keep personal contact details and raw responses out of the public repository.
